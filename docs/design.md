# p98lib 設計メモ

対象: PC-98(386以上)、WebNP2(NP2kai) + FreeDOS(98) 上で動く C ゲーム向けの最小
グラフィックライブラリ。コンパイラは WorkbenchNP2 が提供する SmallerC の
**huge model**。今回のスコープは「画面が出て、塗れて、ページ交換できる」ところまで。
キーボードとスプライトは未実装(下の「未実装: キーボード/スプライトの設計」参照)。

仕様の根拠は `WebNP2-wiki`(Graphics.md / Timing-and-Interrupts.md)と、
実機ではなく **WebNP2(np2kai)上での実測**。third-partyのライブラリ実装(master.lib等)
のソースは一切参照していない。

## ビルド経路

### ビルド経路の変遷: asm()ブロック→別ファイルのNASM+複数オブジェクトリンク

**2026-09の最初の依頼時点**の想定は「C(SmallerC huge)とライブラリ本体(NASM)を
リンクする」だったが、その時点で調べた結果、WorkbenchNP2 の
`toolchain/compile-core.mjs` は

- Cソース **1本** を smlrpp → smlrc → nasm → smlrl の順で処理し、
- smlrl のリンクも **1つの.oとlcdh.aのリンクだけ**をサポートしていて、
- 複数の.oをまとめてリンクする経路は提供されていない

ことが分かった。当時は依頼の前提が「WorkbenchNP2側のファイルは変更しない」
だったため、SmallerC (huge model) の `asm("assembly code");`
(文字列をそのまま出力に埋め込むだけのインラインアセンブリ。
`toolchain/smallerc-src/v0100/doc/smlrc.md` に記載があり、コンパイラの
コード生成へそのまま流れる本物のNASM構文)を使い、`src/p98.c` 1本
(+ `include/p98.h`)で完結させ、WorkbenchNP2 側を一切変更しない形にしていた。
ただしこの方式は「別ファイルにしてリンクする」のではなく「Cの関数の中に
埋め込む」形であり、ユーザーのCとライブラリのCを毎回**1つのCソースへ
文字列連結してコンパイルするunityビルド**(後述)とセットだった。

**2026-09の今回の依頼で前提が変わり**、WorkbenchNP2 側を変更してよいことに
なったため、unityビルドと asm() 埋め込み方式をやめ、次の形へ移行した:

- WorkbenchNP2 の `compile-core.mjs` に
  `opts.extraLinkInputs`(追加の`.o`/`.a`をリンク段で束ねる)と
  `compileToObjectWithFactories`(Cソース1本をリンクせずELFオブジェクトへ)を
  追加してもらった(WorkbenchNP2 `docs/smallerc-wasm.md` 参照)。
- `p98__outb`(out port,val)は本物の別ファイル `src/p98_asm.asm`(NASM)へ
  切り出し、`toolchain/assemble.mjs` でELFオブジェクト化した。
- `tools/build.mjs` は「`src/p98.c`(ライブラリ)を単独でオブジェクト化」
  「`src/p98_asm.asm`を単独でアセンブル」「ユーザーの`.c`をコンパイルする際に
  その2つを`extraLinkInputs`として渡してリンク」という3段構成にした。
  C同士(ライブラリ/ユーザー)を文字列連結する処理はもう無い。
- 残りのプリミティブ(`p98__inb`/`p98__fillmem`/`p98__peekb`/`p98__pokeb`/
  割り込みベクタ操作)は引き続き `asm()` ブロックのままにした。全部を
  別ファイルへ移す必要は無く、「別ファイルのNASM→ELFオブジェクト→リンク」
  という経路が本当に動くことを示すのが今回のスコープだったため。

この移行にあたって、huge modelでの関数呼び出しの実際のABIを
WorkbenchNP2 `toolchain/smallerc-src/v0100/cgx86.c` のコード生成を実際に
コンパイルして確認した(詳細は次節の実測結果と同じ手法)。呼び出し側
(smlrcが生成するC側のコード)は `db 0x9A`(far call)+ `section .relot` 経由の
遠隔呼び出しを自動生成するため、**呼ばれる側の手書きNASMは特別なことをする
必要が無く**、プロローグ/エピローグ(`push ebp` / `movzx ebp, sp` …
`o32 leave` / `retf`)をsmlrc生成コードに合わせるだけでよいと分かった。
この理解が正しいことは、WorkbenchNP2側の実行検証
(`toolchain/verify-link-multi-object.mjs`)とp98lib側の`tools/verify.mjs`
(18項目全通過、移行前と同じ期待値のVRAMバイト列と一致)の両方で
実機(WebNP2+FreeDOS(98))実行を通して確認済み。

### asm() ブロックの安全な書き方(重要な実測結果)

SmallerC の `asm()` は **Cの変数を自動でオペランドに束縛してくれない**
(GCCの拡張asmのような `"=r"(x)` は無い)。素朴に `asm("mov al, [g_val]")` の
ように **グローバル変数をラベル名で直接触るのは危険**だと分かった。

理由: huge model はグローバル変数へアクセスするたびに、コンパイラが
「そのシンボルのリンク時アドレス(単純な realmode の linear address =
segment*16+offset)」から

```nasm
ror esi, 4      ; 下位4bitを上位へ回す
mov ds, si       ; segment = linear >> 4
shr esi, 28      ; 残りの下位4bitをoffsetとして使う
```

という正規化を **毎回コンパイラ自身が生成して** DS を積み直している
(`static unsigned long g_count; void __interrupt h(void){ g_count++; }` を
実際にコンパイルして確認した)。つまり「直前の文でDSがセットされたはず」という
前提はコンパイラの内部実装に依存した推測に過ぎず、当てにできない。

そこで asm() ブロックは次の2パターンだけに限定した(どちらもDSの状態に依存しない):

1. **関数引数をスタック相対 `[bp+N]` で読む。** huge modelでは関数プロローグが
   必ず `push ebp` / `movzx ebp, sp` で、各引数は型によらず **4バイトスロット**
   を占める。オフセットは当てずっぽうではなく、SmallerC自身が出力する
   `; loc x : (@N)` というコメント(`-huge`でコンパイルした結果に実際に出る)
   で確認した実測値。スタックは SS ベースの素直な実アドレスなので、
   huge modelのグローバル変数のような正規化は不要で安全。
2. **VRAMなどのハードウェアセグメントをES に直接ロードする。** `0xA800` のような
   固定セグメント値は引数からそのまま `mov ax,[bp+N]; mov es,ax` でロードできる
   (これもDS非依存)。

この2つだけで `p98__outb` / `p98__inb` / `p98__fillmem`(GRCGの元でのrep stosb
一括書き込み)/ `p98__peekb` / `p98__pokeb` / 割り込みベクタ操作を実装した
(`src/p98.c` 冒頭のプリミティブ群)。Cのグローバル状態(退避したパレット値、
現在の描画ページ等)は **すべて普通のC文で読み書き**し、asm()からは触らない。

### `__interrupt` 関数

Ctrl+C (INT 23h) を無害化するハンドラは、SmallerCの `void __interrupt f(void)`
を使った。huge modelでの `__interrupt` は実際にコンパイルして確認した結果、

- 全汎用レジスタ・セグメントレジスタを `push`
- 通常の関数と同じプロローグ/ボディ
- `pop` で全部戻して **`iret`** で終わる(`retf`ではない)

という、素直な「本物の割り込みハンドラ」になっていた。ハンドラ自身の
アドレス(セグメント:オフセット)は `(unsigned long)(void*)ハンドラ関数` を
`>>4` / `&0xF` するだけで求まる(このキャストで得られる整数値もまた、
上記と同じ「単純な linear address」であることを実測で確認した)。

### 参照の仕方: WorkbenchNP2への相対パス依存(コピーではない)

`tools/build.mjs` は WorkbenchNP2 の `toolchain/*.mjs` と `smlrc-wasm/*` を
**`../WorkbenchNP2` への相対パスでそのまま import/require** する。
ビルド済み成果物をp98lib側へコピーする方式にはしなかった。理由:

- huge model対応は2026-09時点でWorkbenchNP2 masterに入ったばかりで、
  今後も更新される見込みが高い。コピーすると鮮度が失われる
- wasm本体を含めて数MB〜十数MBの重複バイナリを別リポジトリに抱えたくない
- WorkbenchNP2側を書き換えないので、依存が壊れたときの原因切り分けがしやすい

欠点: WorkbenchNP2 チェックアウトが `p98lib` の隣(`../WorkbenchNP2`)に無いと
ビルドできない。開発機ではこの前提を満たしている。

### unityビルド(1翻訳単位)は廃止済み(2026-09)

以前は `compile-core.mjs` がCソース1本しか受け付けなかったため、
`tools/build.mjs` は `src/p98.c` の本文とユーザーの `.c` を**文字列として
連結**してから1回でコンパイルしていた。現在は前節の通り、WorkbenchNP2側に
`compileToObjectWithFactories` と `opts.extraLinkInputs` が追加されたため、
ライブラリのCとユーザーのCを**別々にコンパイルしてリンク**する形になり、
この文字列連結は行っていない。`p98.h` は変わらず両方の翻訳単位へ
includeFilesとして渡し、`#include "p98.h"` で解決する。

## ハードウェア仕様(実測で確認したこと)

`WebNP2-wiki/Graphics.md` に載っている内容をそのまま使った箇所(GRCGの手順、
プレーンのセグメント、パレットポート、ページ切り替えポート等)は再掲しない。
以下は **今回あらためて実測して確認・補足した**事項。

### パレット(0xA8/0xAA/0xAC/0xAE)は読み書きとも実測で確認

`p98_init()`/`p98_quit()` の実装は、初期化前に16色ぶんのG/R/Bをポートから
読み出して保存し、終了時に書き戻す。`docs/verify-log.md` の "初期化/終了の
状態退避・復元" で、変更前後の値が一致することを確認した。

### 表示ページ/描画ページ(0xA4/0xA6)は「同じアドレスの中身が入れ替わる」方式

`Graphics.md`には「0xA4/0xA6でページを切り替えられる」とだけ書かれていて、
**裏ページの物理アドレスが `0xA8000+一定オフセット` のように別に存在するのか、
それとも `0xA8000` という同じアドレスの中身がバンク切り替えされるのか**は
書かれていなかった。

最初 `0xA8000 + 0x8000バイト`(セグメント単位で+0x0800)が裏ページだろうと
仮説を立てて実装したが、実測(`docs/verify-log.md`)で**誤り**だと分かった。
プレーン同士が0x8000バイト間隔で並んでいる(青=0xA8000,赤=0xB0000,…)ため、
この仮説だと「あるプレーンの裏ページ」が「別のプレーンの表ページ」と
物理的に重なってしまい、実際にVRAMが化けた。

正しい挙動は **「0xA8000等は常に “今CPUから見えているページ” を指す」**
方式(バンク切り替え)だった。ゲスト自身が `p98_flip()` の前後で同じアドレス
(`0xA8000`)を読み直すと、切り替え後は正しく別ページの内容が読める
(`docs/verify-log.md` 参照)。この結果を踏まえて `p98lib` の実装
(`src/p98.c`)からは「裏ページの物理アドレスを直接計算する」コードを
削除し、常に `0xA8000` 等の基準アドレスへ描く(表示/描画の切り替えは
ポート`0xA4`/`0xA6`だけに任せる)方式にした。

**この結果は np2kai(WebNP2)上でのエミュレーション実装の実測であり、
実機のバンク切り替え方式が本当にこの通りかは未確認。**

### INT 23h(Ctrl+C)を無害化する方式

`WebNP2-wiki` にはCtrl+C対策の記載が無かったため、DOSの一般的な作法
(AH=35hでベクタ取得→AH=25hで差し替え→終了時に戻す)をそのまま適用した。
`docs/verify-log.md` で、

1. ゲスト自身が読んでも `p98_init()` の前後でベクタが実際に変わっている
   (陽性対照: 「戻しただけで何も変えていない」を誤って合格にしないための確認)
2. `p98_quit()` 後に元の値へ戻っている
3. IVT(0000:0000セグメントの008Ch番地)を外部(np2kai本体)からメモリダンプ
   しても同じ結果になる

の3点を確認した。

## 未確認・限界(正直に書く)

- **画面モードの「復元」は、読み出しではなく既知の既定値への上書き。**
  `AH=0x42`のモード設定ポート/GDCのグラフィック表示ON/OFF(`0xA2`)や
  16色モード(`0x6A`)は、WebNP2-wikiに「読み出せる」という記載が無く、
  今回の調査でも読み出し方法を確認できなかった。そのため `p98_quit()` は
  「起動直後のFreeDOS(98)コンソールは400ライン・表画面(`CH=0xC0`)である」
  という前提のもとに、その既知の値へ**上書き**しているだけで、
  「呼び出し前の実際の値を読んで戻す」処理にはなっていない。
  検証は「`p98_quit()`後にDOSプロンプトが正常に表示・入力できる」ことで
  間接的に確認しているに留まる(`docs/verify-log.md`)。
- 表示ページ/描画ページのバンク切り替えの仕組みは実機未検証(上記)。
- 400ライン以外の画面モード、8色モードは未検証(スコープ外)。
- EGCは使っていない(WebNP2-wiki記載のとおり、マスク等の効果が未検証のため)。

## 公開API (include/p98.h)

```c
int p98_init(void);
void p98_quit(void);
void p98_wait_vsync(void);
void p98_flip(void);
unsigned long p98_frames(void);
void p98_clear(int color);
void p98_fill_rect(int x, int y, int w, int h, int color);
void p98_set_palette(int index, int r, int g, int b);
```

`p98_fill_rect()` は画面外・負のx/y・幅/高さ0以下をクリップする。バイト境界に
揃わない矩形の左右端は、GRCGではなく1バイト単位のread-modify-write
(`p98__peekb`/`p98__pokeb`)でビット単位に塗る。GRCGは「バイト境界に完全に
収まる中央部分」と `p98_clear()`(画面全体)だけに使い、1回のASM呼び出しで
1プレーン分(32000バイト)を書き切る。

## キーボード(実装済み、2026-09。BIOS(INT 18h)キーセンス方式)

```c
void p98_poll(void);               /* このフレーム分の入力を取り込む */
int  p98_key_down(int scancode);   /* 押している間ずっと真 */
int  p98_key_pressed(int scancode);/* このフレームで新規に押された時だけ真(押しっぱなしでは1回だけ) */
int  p98_key_getch(void);          /* BIOSのキーバッファから1文字。無ければ0 */
```

実装は `src/p98.c` の「キーボード(BIOS INT 18h方式)」節、`tests/probe_key.c` /
`tests/p98_broken_nodiff.c`、`tools/verify.mjs` の「キーボード」ブロック。

### 方式転換の経緯: IRQ1直接受信 → BIOSキーセンス

**当初(2026-09前半)はキーボード割り込み(IRQ1 = INT 09h、実測で確認)を
自前の`__interrupt`ハンドラで奪う方式**を実装していた(押下状態の管理、
EOI必須であること、SHIFT記号変換の全数実測など、当時の実測結果は
`docs/verify-log.md`と`WebNP2-wiki` `Keyboard.md`/`Timing-and-Interrupts.md`
に書き戻し済みで、そちらに知識として残している。以下はこの設計を
やめた理由)。

**やめた理由(実測で確認): 生のIRQ1レベルではキーリピートを止められない。**
キーを500ms以上ホールドすると、生のIRQ1割り込みレベルでも
「離した(break)→押した(make)」のペアが一定間隔(約500ms後から約50ms間隔)
で繰り返し来ることを実測した(0x1Dを1.4秒ホールドし、`p98_key_pressed()`が
18回真になった)。「直前にdownでなかった場合だけedgeを立てる」という
デバウンスを試したが、リピートのたびに本物のbreakコードが先に来てから
次のmakeが来るため効果が無かった(対策前後で18回→17回とほぼ変わらず)。
「押しっぱなし」と「素早く離して押し直す」をスキャンコードの並びだけから
区別する方法が無く、**raw割り込みレベルでは本質的に解決できない**と判断した。

**ユーザー本人が1996年に書いたPC-98ゲーム(`WorkbenchNP2/samples/legacy/saka/
SAKA.ASM`、`SHUTING.ASM`。ともにユーザー自身の著作物)が`INT 18h AH=04h`
(キーセンス)を使っており、当時これでキーリピートに悩まなかった**という
実例に基づき、BIOSのキーセンス方式へ切り替えた。キーセンスは「今その瞬間
押しているか」を読むだけの状態読み取りで、割り込みの回数を数える方式では
ないため、リピートの影響を原理的に受けない。

### INT 18h AH=04h(キーセンス)の実測

Wikiの`Keyboard.md`には当時この呼び出しの記載が無かったため、実装前に
実測で仕様を確定した。

**手がかり(ユーザー本人の著作物、参照可)**: `SAKA.ASM`/`SHUTING.ASM`の
実例から、`AL`にグループ番号(0=ESC等を含む先頭グループ、6=SPACE、
7=カーソルキー等)を渡し、`AH=04h`で`INT 18h`を呼ぶと、`AH`にそのグループの
押下状態がビットで返る、という規則を読み取った。ESC(scancode 0x00)が
group0のbit0、SPACE(0x34)がgroup6のbit4、UP/RIGHT/DOWN/LEFT(0x3A/0x3C/0x3D/0x3B)
がgroup7のbit2/4/5/3、F1〜F5(0x62〜0x66)がgroup12のbit2〜6、という
11個のサンプル全てが「`group = scancode >> 3`、`bit = scancode & 7`」という
規則に一致した(ソースコードの読み出しであって、ROM内の変換テーブルを
読み出す・移植する行為ではない。あくまで「1996年当時の公開されたPC-98向け
ゲームプログラムが、この呼び出しをどう使っていたか」という実例の参照)。

**上記の規則をnp2kai上で独立に実測して確認した**: p98libのハンドラは
一切インストールせず、`np2.sendKey()`で0x1D('a', group3 bit5)と
0x3D(DOWN, group7 bit5)を同時に押しっぱなしにし、押す前/押している間/
離した後の3点で`AH=04h`を呼んだ。結果、押している間だけ両方とも期待どおり
`0x20`(bit5)が返り、離すと`0`に戻った。この2件の実測は`SAKA.ASM`/
`SHUTING.ASM`の実例と完全に一致した(使い捨てプローブ、コミットには
残していない)。

**判明した副作用(実測で気づいた重要な注意点)**: キーセンス(AH=04h)は
BIOSのタイプアヘッドバッファを**消費しない**。そのため、`sendKey`で
押しっぱなしにしたキーはBIOSの16件バッファに溜まったままになり、
**プログラム終了時に空にしないと、戻った先のCOMMAND.COM(や次のプログラム)
がそれを入力として読んでしまう**ことを実測で確認した(この副作用に
気づかず、ずっと「プロンプトの検出がタイムアウトする」という現象に
悩まされた。原因を切り分けるため、①`AH=04h`を1回だけ呼ぶ最小構成、
②vsync待ちループだけの構成、③sendKeyだけ足した構成、を順に切り分けて
測り、「sendKeyで注入したキーをプログラムが消費しないまま終了する」
ことが原因だと特定した)。この副作用への対策として、`p98_quit()`で
必ず`INT 18h AH=01h`(有無確認)/`AH=00h`(取り出し)のループでバッファを
空にするようにした。

これらはすべて **np2kai(WebNP2)上の実測**であり、実機PC-98のBIOSが
本当にこの通りかは未確認(他の節と同じ限界)。

### 実装方針

- **押下状態はポーリング方式。** `p98_poll()`が16グループぶん`INT 18h AH=04h`
  を呼び、結果を`p98__key_cur_down[16]`(現在)と`p98__key_prev_down[16]`
  (前回)へ保存する。`p98__key_pressed_snap[16]`は`cur & ~prev`
  (前回は0で今回は1のビットだけ)として計算する。これにより、
  押しっぱなしの間はリピートが何度来ても`pressed`は最初の1回しか
  真にならない(BIOSのキーリピートの影響を受けない)。
- 割り込みハンドラ・PIC操作・ベクタ横取りは一切行わない(IRQ1方式の
  ときにあった`cli`/`sti`保護やEOI処理は不要になった)。
- 文字入力はBIOSのキーバッファ(`INT 18h AH=01h`で有無確認、`AH=00h`で
  取り出し)をそのまま使う。**SHIFT/CAPS/CTRL等の文字変換は自前で行わず、
  BIOSが変換した結果をそのまま返す**(`WebNP2-wiki` `Keyboard.md`参照)。
  以前実測して`src/p98.c`に持っていたSHIFT記号変換テーブル・CTRL変換式・
  CAPSトグル管理は不要になったため削除した(**知識としては
  `docs/verify-log.md`とWikiに残っている**ため、失われてはいない)。
- **`p98_quit()`で必ずBIOSのキーバッファを空にする。** 前述の副作用
  (押しっぱなしのキーがバッファに残って次のプログラムに漏れる)を
  防ぐため。

### この方式で解消したこと・新たに生じた制限

- **CAPSロックのBIOS側状態との同期のずれ(旧IRQ1方式での懸案)は解消した。**
  BIOSのIRQ1を一切奪わないため、CAPSの処理は常にBIOSが行う。実測
  (`p98_init()`中にCAPSをタップしてから`a`を`p98_key_getch()`で読むと
  `0x41`('A')が正しく返る)で確認した。
- **新たな制限: `p98_poll()`を呼ぶ間隔より短い「ちょん押し」を取りこぼす。**
  IRQ1直接受信方式では、割り込みハンドラが押下の瞬間を専用のedgeビットに
  記録するため、1フレーム未満の短い押下でも次の`p98_poll()`で拾えていた。
  BIOSキーセンス方式は「今その瞬間押しているか」を読むだけの状態読み取り
  のため、`p98_poll()`と`p98_poll()`の間に完全に収まる押下(押してから
  次のpollより前に離す)は`down`にも`pressed`にも一切反映されない。
  この制限はユーザー了承済みで、対策はしていない。

### 未確認・既知の限界(まとめ)

- 実機での確認は行っていない(他の節と同じ限界。すべてnp2kai上の実測)。
- BIOSキーセンス(AH=04h)の全16グループ×8bit=128スキャンコードすべてを
  実測したわけではなく、`SAKA.ASM`/`SHUTING.ASM`の実例(11サンプル)と、
  上記の独立した実測(2サンプル)で規則を確認したに留まる。規則
  (`group=scancode>>3`、`bit=scancode&7`)自体は一貫していたため、
  未実測のグループも同じ規則に従うと考えているが、全数実測はしていない。
- 1フレーム未満の押下を取りこぼす制限は前述のとおり(ユーザー了承済み)。
