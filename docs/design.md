# p98lib 設計メモ

対象: PC-98(386以上)、WebNP2(NP2kai) + FreeDOS(98) 上で動く C ゲーム向けの最小
グラフィックライブラリ。コンパイラは WorkbenchNP2 が提供する SmallerC の
**huge model**。画面初期化・塗り・ページ交換・キーボード・スプライト
(CPU合成・EGC経路の両方)を実装済み。実装済みのEGC経路(4プレーン
同時書き込みのみ使用)はCPU合成より速くならなかったが、**その後の
追試で、EGCのシフト・マスク自体は「読んでから書く」正しい手順を踏めば
機能することが判明した**(スプライト描画への本格的な組み込みは次回)。
詳細は下の「EGCによるスプライト高速化」節、および同節末尾の訂正
「EGCのシフト・マスク: 訂正」参照。無理に速く見せていない。

仕様の根拠は `WebNP2-wiki`(Graphics.md / Timing-and-Interrupts.md)と、
実機ではなく **WebNP2(np2kai)上での実測**。third-partyのライブラリ実装(master.lib等)
のソースは一切参照していない。

## ビルド経路

### ビルド経路の変遷: asm()ブロック→別ファイルのNASM+複数オブジェクトリンク

**2026-09の最初の依頼時点**の想定は「C(SmallerC huge)とライブラリ本体(NASM)を
リンクする」だったが、その時点で調べた結果、WorkbenchNP2 の
`toolchain/compile-core.mjs` は

- Cソース **1本** を smlrpp → smlrc → nasm → smlrl の順で処理し、
- smlrl のリンクも **1つの.oとlcdh.aのリンクだけ**をサポートしていて、
- 複数の.oをまとめてリンクする経路は提供されていない

ことが分かった。当時は依頼の前提が「WorkbenchNP2側のファイルは変更しない」
だったため、SmallerC (huge model) の `asm("assembly code");`
(文字列をそのまま出力に埋め込むだけのインラインアセンブリ。
`toolchain/smallerc-src/v0100/doc/smlrc.md` に記載があり、コンパイラの
コード生成へそのまま流れる本物のNASM構文)を使い、`src/p98.c` 1本
(+ `include/p98.h`)で完結させ、WorkbenchNP2 側を一切変更しない形にしていた。
ただしこの方式は「別ファイルにしてリンクする」のではなく「Cの関数の中に
埋め込む」形であり、ユーザーのCとライブラリのCを毎回**1つのCソースへ
文字列連結してコンパイルするunityビルド**(後述)とセットだった。

**2026-09の今回の依頼で前提が変わり**、WorkbenchNP2 側を変更してよいことに
なったため、unityビルドと asm() 埋め込み方式をやめ、次の形へ移行した:

- WorkbenchNP2 の `compile-core.mjs` に
  `opts.extraLinkInputs`(追加の`.o`/`.a`をリンク段で束ねる)と
  `compileToObjectWithFactories`(Cソース1本をリンクせずELFオブジェクトへ)を
  追加してもらった(WorkbenchNP2 `docs/smallerc-wasm.md` 参照)。
- `p98__outb`(out port,val)は本物の別ファイル `src/p98_asm.asm`(NASM)へ
  切り出し、`toolchain/assemble.mjs` でELFオブジェクト化した。
- `tools/build.mjs` は「`src/p98.c`(ライブラリ)を単独でオブジェクト化」
  「`src/p98_asm.asm`を単独でアセンブル」「ユーザーの`.c`をコンパイルする際に
  その2つを`extraLinkInputs`として渡してリンク」という3段構成にした。
  C同士(ライブラリ/ユーザー)を文字列連結する処理はもう無い。
- 残りのプリミティブ(`p98__inb`/`p98__fillmem`/`p98__peekb`/`p98__pokeb`/
  割り込みベクタ操作)は引き続き `asm()` ブロックのままにした。全部を
  別ファイルへ移す必要は無く、「別ファイルのNASM→ELFオブジェクト→リンク」
  という経路が本当に動くことを示すのが今回のスコープだったため。

この移行にあたって、huge modelでの関数呼び出しの実際のABIを
WorkbenchNP2 `toolchain/smallerc-src/v0100/cgx86.c` のコード生成を実際に
コンパイルして確認した(詳細は次節の実測結果と同じ手法)。呼び出し側
(smlrcが生成するC側のコード)は `db 0x9A`(far call)+ `section .relot` 経由の
遠隔呼び出しを自動生成するため、**呼ばれる側の手書きNASMは特別なことをする
必要が無く**、プロローグ/エピローグ(`push ebp` / `movzx ebp, sp` …
`o32 leave` / `retf`)をsmlrc生成コードに合わせるだけでよいと分かった。
この理解が正しいことは、WorkbenchNP2側の実行検証
(`toolchain/verify-link-multi-object.mjs`)とp98lib側の`tools/verify.mjs`
(18項目全通過、移行前と同じ期待値のVRAMバイト列と一致)の両方で
実機(WebNP2+FreeDOS(98))実行を通して確認済み。

### asm() ブロックの安全な書き方(重要な実測結果)

SmallerC の `asm()` は **Cの変数を自動でオペランドに束縛してくれない**
(GCCの拡張asmのような `"=r"(x)` は無い)。素朴に `asm("mov al, [g_val]")` の
ように **グローバル変数をラベル名で直接触るのは危険**だと分かった。

理由: huge model はグローバル変数へアクセスするたびに、コンパイラが
「そのシンボルのリンク時アドレス(単純な realmode の linear address =
segment*16+offset)」から

```nasm
ror esi, 4      ; 下位4bitを上位へ回す
mov ds, si       ; segment = linear >> 4
shr esi, 28      ; 残りの下位4bitをoffsetとして使う
```

という正規化を **毎回コンパイラ自身が生成して** DS を積み直している
(`static unsigned long g_count; void __interrupt h(void){ g_count++; }` を
実際にコンパイルして確認した)。つまり「直前の文でDSがセットされたはず」という
前提はコンパイラの内部実装に依存した推測に過ぎず、当てにできない。

そこで asm() ブロックは次の2パターンだけに限定した(どちらもDSの状態に依存しない):

1. **関数引数をスタック相対 `[bp+N]` で読む。** huge modelでは関数プロローグが
   必ず `push ebp` / `movzx ebp, sp` で、各引数は型によらず **4バイトスロット**
   を占める。オフセットは当てずっぽうではなく、SmallerC自身が出力する
   `; loc x : (@N)` というコメント(`-huge`でコンパイルした結果に実際に出る)
   で確認した実測値。スタックは SS ベースの素直な実アドレスなので、
   huge modelのグローバル変数のような正規化は不要で安全。
2. **VRAMなどのハードウェアセグメントをES に直接ロードする。** `0xA800` のような
   固定セグメント値は引数からそのまま `mov ax,[bp+N]; mov es,ax` でロードできる
   (これもDS非依存)。

この2つだけで `p98__outb` / `p98__inb` / `p98__fillmem`(GRCGの元でのrep stosb
一括書き込み)/ `p98__peekb` / `p98__pokeb` / 割り込みベクタ操作を実装した
(`src/p98.c` 冒頭のプリミティブ群)。Cのグローバル状態(退避したパレット値、
現在の描画ページ等)は **すべて普通のC文で読み書き**し、asm()からは触らない。

### `__interrupt` 関数

Ctrl+C (INT 23h) を無害化するハンドラは、SmallerCの `void __interrupt f(void)`
を使った。huge modelでの `__interrupt` は実際にコンパイルして確認した結果、

- 全汎用レジスタ・セグメントレジスタを `push`
- 通常の関数と同じプロローグ/ボディ
- `pop` で全部戻して **`iret`** で終わる(`retf`ではない)

という、素直な「本物の割り込みハンドラ」になっていた。ハンドラ自身の
アドレス(セグメント:オフセット)は `(unsigned long)(void*)ハンドラ関数` を
`>>4` / `&0xF` するだけで求まる(このキャストで得られる整数値もまた、
上記と同じ「単純な linear address」であることを実測で確認した)。

### 参照の仕方: WorkbenchNP2への相対パス依存(コピーではない)

`tools/build.mjs` は WorkbenchNP2 の `toolchain/*.mjs` と `smlrc-wasm/*` を
**`../WorkbenchNP2` への相対パスでそのまま import/require** する。
ビルド済み成果物をp98lib側へコピーする方式にはしなかった。理由:

- huge model対応は2026-09時点でWorkbenchNP2 masterに入ったばかりで、
  今後も更新される見込みが高い。コピーすると鮮度が失われる
- wasm本体を含めて数MB〜十数MBの重複バイナリを別リポジトリに抱えたくない
- WorkbenchNP2側を書き換えないので、依存が壊れたときの原因切り分けがしやすい

欠点: WorkbenchNP2 チェックアウトが `p98lib` の隣(`../WorkbenchNP2`)に無いと
ビルドできない。開発機ではこの前提を満たしている。

### unityビルド(1翻訳単位)は廃止済み(2026-09)

以前は `compile-core.mjs` がCソース1本しか受け付けなかったため、
`tools/build.mjs` は `src/p98.c` の本文とユーザーの `.c` を**文字列として
連結**してから1回でコンパイルしていた。現在は前節の通り、WorkbenchNP2側に
`compileToObjectWithFactories` と `opts.extraLinkInputs` が追加されたため、
ライブラリのCとユーザーのCを**別々にコンパイルしてリンク**する形になり、
この文字列連結は行っていない。`p98.h` は変わらず両方の翻訳単位へ
includeFilesとして渡し、`#include "p98.h"` で解決する。

## ハードウェア仕様(実測で確認したこと)

`WebNP2-wiki/Graphics.md` に載っている内容をそのまま使った箇所(GRCGの手順、
プレーンのセグメント、パレットポート、ページ切り替えポート等)は再掲しない。
以下は **今回あらためて実測して確認・補足した**事項。

### パレット(0xA8/0xAA/0xAC/0xAE)は読み書きとも実測で確認

`p98_init()`/`p98_quit()` の実装は、初期化前に16色ぶんのG/R/Bをポートから
読み出して保存し、終了時に書き戻す。`docs/verify-log.md` の "初期化/終了の
状態退避・復元" で、変更前後の値が一致することを確認した。

### 表示ページ/描画ページ(0xA4/0xA6)は「同じアドレスの中身が入れ替わる」方式

`Graphics.md`には「0xA4/0xA6でページを切り替えられる」とだけ書かれていて、
**裏ページの物理アドレスが `0xA8000+一定オフセット` のように別に存在するのか、
それとも `0xA8000` という同じアドレスの中身がバンク切り替えされるのか**は
書かれていなかった。

最初 `0xA8000 + 0x8000バイト`(セグメント単位で+0x0800)が裏ページだろうと
仮説を立てて実装したが、実測(`docs/verify-log.md`)で**誤り**だと分かった。
プレーン同士が0x8000バイト間隔で並んでいる(青=0xA8000,赤=0xB0000,…)ため、
この仮説だと「あるプレーンの裏ページ」が「別のプレーンの表ページ」と
物理的に重なってしまい、実際にVRAMが化けた。

正しい挙動は **「0xA8000等は常に “今CPUから見えているページ” を指す」**
方式(バンク切り替え)だった。ゲスト自身が `p98_flip()` の前後で同じアドレス
(`0xA8000`)を読み直すと、切り替え後は正しく別ページの内容が読める
(`docs/verify-log.md` 参照)。この結果を踏まえて `p98lib` の実装
(`src/p98.c`)からは「裏ページの物理アドレスを直接計算する」コードを
削除し、常に `0xA8000` 等の基準アドレスへ描く(表示/描画の切り替えは
ポート`0xA4`/`0xA6`だけに任せる)方式にした。

**この結果は np2kai(WebNP2)上でのエミュレーション実装の実測であり、
実機のバンク切り替え方式が本当にこの通りかは未確認。**

### INT 23h(Ctrl+C)を無害化する方式

`WebNP2-wiki` にはCtrl+C対策の記載が無かったため、DOSの一般的な作法
(AH=35hでベクタ取得→AH=25hで差し替え→終了時に戻す)をそのまま適用した。
`docs/verify-log.md` で、

1. ゲスト自身が読んでも `p98_init()` の前後でベクタが実際に変わっている
   (陽性対照: 「戻しただけで何も変えていない」を誤って合格にしないための確認)
2. `p98_quit()` 後に元の値へ戻っている
3. IVT(0000:0000セグメントの008Ch番地)を外部(np2kai本体)からメモリダンプ
   しても同じ結果になる

の3点を確認した。

## 未確認・限界(正直に書く)

- **画面モードの「復元」は、読み出しではなく既知の既定値への上書き。**
  `AH=0x42`のモード設定ポート/GDCのグラフィック表示ON/OFF(`0xA2`)や
  16色モード(`0x6A`)は、WebNP2-wikiに「読み出せる」という記載が無く、
  今回の調査でも読み出し方法を確認できなかった。そのため `p98_quit()` は
  「起動直後のFreeDOS(98)コンソールは400ライン・表画面(`CH=0xC0`)である」
  という前提のもとに、その既知の値へ**上書き**しているだけで、
  「呼び出し前の実際の値を読んで戻す」処理にはなっていない。
  検証は「`p98_quit()`後にDOSプロンプトが正常に表示・入力できる」ことで
  間接的に確認しているに留まる(`docs/verify-log.md`)。
- 表示ページ/描画ページのバンク切り替えの仕組みは実機未検証(上記)。
- 400ライン以外の画面モード、8色モードは未検証(スコープ外)。
- EGCは使っていない(WebNP2-wiki記載のとおり、マスク等の効果が未検証のため)。

## 公開API (include/p98.h)

```c
int p98_init(void);
void p98_quit(void);
void p98_wait_vsync(void);
void p98_flip(void);
unsigned long p98_frames(void);
void p98_clear(int color);
void p98_fill_rect(int x, int y, int w, int h, int color);
void p98_set_palette(int index, int r, int g, int b);
```

`p98_fill_rect()` は画面外・負のx/y・幅/高さ0以下をクリップする。バイト境界に
揃わない矩形の左右端は、GRCGではなく1バイト単位のread-modify-write
(`p98__peekb`/`p98__pokeb`)でビット単位に塗る。GRCGは「バイト境界に完全に
収まる中央部分」と `p98_clear()`(画面全体)だけに使い、1回のASM呼び出しで
1プレーン分(32000バイト)を書き切る。

## キーボード(実装済み、2026-09。BIOS(INT 18h)キーセンス方式)

```c
void p98_poll(void);               /* このフレーム分の入力を取り込む */
int  p98_key_down(int scancode);   /* 押している間ずっと真 */
int  p98_key_pressed(int scancode);/* このフレームで新規に押された時だけ真(押しっぱなしでは1回だけ) */
int  p98_key_getch(void);          /* BIOSのキーバッファから1文字。無ければ0 */
```

実装は `src/p98.c` の「キーボード(BIOS INT 18h方式)」節、`tests/probe_key.c` /
`tests/p98_broken_nodiff.c`、`tools/verify.mjs` の「キーボード」ブロック。

### 方式転換の経緯: IRQ1直接受信 → BIOSキーセンス

**当初(2026-09前半)はキーボード割り込み(IRQ1 = INT 09h、実測で確認)を
自前の`__interrupt`ハンドラで奪う方式**を実装していた(押下状態の管理、
EOI必須であること、SHIFT記号変換の全数実測など、当時の実測結果は
`docs/verify-log.md`と`WebNP2-wiki` `Keyboard.md`/`Timing-and-Interrupts.md`
に書き戻し済みで、そちらに知識として残している。以下はこの設計を
やめた理由)。

**やめた理由(実測で確認): 生のIRQ1レベルではキーリピートを止められない。**
キーを500ms以上ホールドすると、生のIRQ1割り込みレベルでも
「離した(break)→押した(make)」のペアが一定間隔(約500ms後から約50ms間隔)
で繰り返し来ることを実測した(0x1Dを1.4秒ホールドし、`p98_key_pressed()`が
18回真になった)。「直前にdownでなかった場合だけedgeを立てる」という
デバウンスを試したが、リピートのたびに本物のbreakコードが先に来てから
次のmakeが来るため効果が無かった(対策前後で18回→17回とほぼ変わらず)。
「押しっぱなし」と「素早く離して押し直す」をスキャンコードの並びだけから
区別する方法が無く、**raw割り込みレベルでは本質的に解決できない**と判断した。

**ユーザー本人が1996年に書いたPC-98ゲーム(`WorkbenchNP2/samples/legacy/saka/
SAKA.ASM`、`SHUTING.ASM`。ともにユーザー自身の著作物)が`INT 18h AH=04h`
(キーセンス)を使っており、当時これでキーリピートに悩まなかった**という
実例に基づき、BIOSのキーセンス方式へ切り替えた。キーセンスは「今その瞬間
押しているか」を読むだけの状態読み取りで、割り込みの回数を数える方式では
ないため、リピートの影響を原理的に受けない。

### INT 18h AH=04h(キーセンス)の実測

Wikiの`Keyboard.md`には当時この呼び出しの記載が無かったため、実装前に
実測で仕様を確定した。

**手がかり(ユーザー本人の著作物、参照可)**: `SAKA.ASM`/`SHUTING.ASM`の
実例から、`AL`にグループ番号(0=ESC等を含む先頭グループ、6=SPACE、
7=カーソルキー等)を渡し、`AH=04h`で`INT 18h`を呼ぶと、`AH`にそのグループの
押下状態がビットで返る、という規則を読み取った。ESC(scancode 0x00)が
group0のbit0、SPACE(0x34)がgroup6のbit4、UP/RIGHT/DOWN/LEFT(0x3A/0x3C/0x3D/0x3B)
がgroup7のbit2/4/5/3、F1〜F5(0x62〜0x66)がgroup12のbit2〜6、という
11個のサンプル全てが「`group = scancode >> 3`、`bit = scancode & 7`」という
規則に一致した(ソースコードの読み出しであって、ROM内の変換テーブルを
読み出す・移植する行為ではない。あくまで「1996年当時の公開されたPC-98向け
ゲームプログラムが、この呼び出しをどう使っていたか」という実例の参照)。

**上記の規則をnp2kai上で独立に実測して確認した**: p98libのハンドラは
一切インストールせず、`np2.sendKey()`で0x1D('a', group3 bit5)と
0x3D(DOWN, group7 bit5)を同時に押しっぱなしにし、押す前/押している間/
離した後の3点で`AH=04h`を呼んだ。結果、押している間だけ両方とも期待どおり
`0x20`(bit5)が返り、離すと`0`に戻った。この2件の実測は`SAKA.ASM`/
`SHUTING.ASM`の実例と完全に一致した(使い捨てプローブ、コミットには
残していない)。

**判明した副作用(実測で気づいた重要な注意点)**: キーセンス(AH=04h)は
BIOSのタイプアヘッドバッファを**消費しない**。そのため、`sendKey`で
押しっぱなしにしたキーはBIOSの16件バッファに溜まったままになり、
**プログラム終了時に空にしないと、戻った先のCOMMAND.COM(や次のプログラム)
がそれを入力として読んでしまう**ことを実測で確認した(この副作用に
気づかず、ずっと「プロンプトの検出がタイムアウトする」という現象に
悩まされた。原因を切り分けるため、①`AH=04h`を1回だけ呼ぶ最小構成、
②vsync待ちループだけの構成、③sendKeyだけ足した構成、を順に切り分けて
測り、「sendKeyで注入したキーをプログラムが消費しないまま終了する」
ことが原因だと特定した)。この副作用への対策として、`p98_quit()`で
必ず`INT 18h AH=01h`(有無確認)/`AH=00h`(取り出し)のループでバッファを
空にするようにした。

これらはすべて **np2kai(WebNP2)上の実測**であり、実機PC-98のBIOSが
本当にこの通りかは未確認(他の節と同じ限界)。

### 実装方針

- **押下状態はポーリング方式。** `p98_poll()`が16グループぶん`INT 18h AH=04h`
  を呼び、結果を`p98__key_cur_down[16]`(現在)と`p98__key_prev_down[16]`
  (前回)へ保存する。`p98__key_pressed_snap[16]`は`cur & ~prev`
  (前回は0で今回は1のビットだけ)として計算する。これにより、
  押しっぱなしの間はリピートが何度来ても`pressed`は最初の1回しか
  真にならない(BIOSのキーリピートの影響を受けない)。
- 割り込みハンドラ・PIC操作・ベクタ横取りは一切行わない(IRQ1方式の
  ときにあった`cli`/`sti`保護やEOI処理は不要になった)。
- 文字入力はBIOSのキーバッファ(`INT 18h AH=01h`で有無確認、`AH=00h`で
  取り出し)をそのまま使う。**SHIFT/CAPS/CTRL等の文字変換は自前で行わず、
  BIOSが変換した結果をそのまま返す**(`WebNP2-wiki` `Keyboard.md`参照)。
  以前実測して`src/p98.c`に持っていたSHIFT記号変換テーブル・CTRL変換式・
  CAPSトグル管理は不要になったため削除した(**知識としては
  `docs/verify-log.md`とWikiに残っている**ため、失われてはいない)。
- **`p98_quit()`で必ずBIOSのキーバッファを空にする。** 前述の副作用
  (押しっぱなしのキーがバッファに残って次のプログラムに漏れる)を
  防ぐため。

### この方式で解消したこと・新たに生じた制限

- **CAPSロックのBIOS側状態との同期のずれ(旧IRQ1方式での懸案)は解消した。**
  BIOSのIRQ1を一切奪わないため、CAPSの処理は常にBIOSが行う。実測
  (`p98_init()`中にCAPSをタップしてから`a`を`p98_key_getch()`で読むと
  `0x41`('A')が正しく返る)で確認した。
- **新たな制限: `p98_poll()`を呼ぶ間隔より短い「ちょん押し」を取りこぼす。**
  IRQ1直接受信方式では、割り込みハンドラが押下の瞬間を専用のedgeビットに
  記録するため、1フレーム未満の短い押下でも次の`p98_poll()`で拾えていた。
  BIOSキーセンス方式は「今その瞬間押しているか」を読むだけの状態読み取り
  のため、`p98_poll()`と`p98_poll()`の間に完全に収まる押下(押してから
  次のpollより前に離す)は`down`にも`pressed`にも一切反映されない。
  この制限はユーザー了承済みで、対策はしていない。

### 未確認・既知の限界(まとめ)

- 実機での確認は行っていない(他の節と同じ限界。すべてnp2kai上の実測)。
- BIOSキーセンス(AH=04h)の全16グループ×8bit=128スキャンコードすべてを
  実測したわけではなく、`SAKA.ASM`/`SHUTING.ASM`の実例(11サンプル)と、
  上記の独立した実測(2サンプル)で規則を確認したに留まる。規則
  (`group=scancode>>3`、`bit=scancode&7`)自体は一貫していたため、
  未実測のグループも同じ規則に従うと考えているが、全数実測はしていない。
- 1フレーム未満の押下を取りこぼす制限は前述のとおり(ユーザー了承済み)。

## スプライト(実装済み、2026-09後半。CPU合成のみ。EGCでの高速化は次回)

### 前提として見つけた既存バグ: 描画ページ1への描画がプレーン境界を壊していた

スプライトの実装に着手する前に、`p98_fill_rect`/`p98_clear`が使っている
`p98__page_stride()`(描画ページが1のとき `+0x0800`(セグメント単位、
=0x8000バイト)を各プレーンのセグメントへ足す実装)が、本ドキュメントの
「表示ページ/描画ページ(0xA4/0xA6)は…」節で**誤りと確認済み・削除したはず**
と書いていた古い仮説(裏ページ=+0x8000バイト)と**全く同じ計算のまま
コードに残っている**ことに気づいた。実測(`docs/verify-log.md`の
`probe_flip`)が確認したのは「0xA8000等は常にバンク切り替えで“今CPUから
見えている面”を指す」方式であり、ソフト側でオフセットを足す必要は無い。
むしろ足すと `P98_SEG_PLANE_B + 0x0800セグメント = P98_SEG_PLANE_R` と
なり、隣のプレーンのセグメントと衝突する(この節の旧仮説の説明と同じ
問題)。

**この既存バグは`p98_init()`直後(初回`p98_flip()`を呼ぶ前、描画ページ=1の
状態)に`p98_fill_rect`/`p98_clear`を呼ぶと即座に踏む**。既存の
`tests/probe_fill.c`が「裏ページのバンク切り替えの疑いに巻き込まれないため」
という理由で意図的に最初に`p98_flip()`してから描画していたため、これまでの
検証(28/28)はこの分岐(`stride!=0`)を一度も通っていなかった。

スプライト実装は`p98_fill_rect`と同じセグメント計算を再利用する前提だった
ため、ここで実際に踏んでから直した(`src/p98.c`から`P98_PAGE_SEG_STRIDE`・
`p98__page_stride()`を削除し、`p98_clear`/`p98_fill_rect`とも常に
`P98_SEG_PLANE_*`をそのまま使うようにした)。修正後も既存の28項目は
全通過することを確認済み(`docs/verify-log.md`)。**今後、描画ページ1への
`p98_fill_rect`/`p98_clear`自体を直接検証するテストは無い**(スプライトの
新規テストが`p98_flip()`前の状態で描画するため、間接的に確認しているに
留まる)。

### データ形式: 4プレーン+別マスクの1bppビットマップ

```c
typedef struct {
    int w, h;
    const unsigned char *planes[4]; /* 青・赤・緑・輝度。1行=ceil(w/8)バイト、MSBが左端 */
    const unsigned char *mask;      /* 1=描画する。同じレイアウト */
} p98_sprite_t;

void p98_draw_sprite(const p98_sprite_t *spr, int x, int y);
```

キーカラー方式ではなく別マスク方式にした理由:
- VRAM自体が4プレーン×1bppなので、変換無しでそのままVRAMへ書ける
  (キーカラー比較のような色空間の変換が要らない)。
- マスクをGRCG非経由(CPU側read-modify-write)のAND/OR合成で扱う前提
  (下記)では、キーカラー比較よりビットマスクの方が単純かつ速い。

スプライトのデータ(ソース側)は**Cの通常のポインタ経由の配列参照**で読む。
huge modelのグローバル/far配列アクセスはコンパイラが自動でDS正規化を
生成するため(design.mdの他の節で説明した「asm()からグローバルを直接
触るのは危険」という制約は、**手書きasm()の中で**グローバル名を直接
触る場合の話であり、普通のC文でのポインタ経由アクセスはコンパイラの
huge model対応がそのまま担当する)、スプライトのソース読み出し側には
新規のasm()は一切要らない。asm()が必要なのはVRAM(ハードウェア固定
セグメント)への書き込み側だけで、これは既存の`p98__peekb`/`p98__pokeb`
と同じパターンで足りる。

### 横1ドットシフトの方式: 事前シフト済みビットマップ vs 描画時シフト

**描画時にCPUでシフトして合成する方式を採用した。** 検討した理由:
- 事前シフト方式(8パターン持つ)はデータサイズが約8倍になる。今回は
  スプライトのデータ形式自体をこのスコープで初めて決める段階で、
  実データの点数・サイズ感がまだ読めなかったため、まずメモリ効率の良い
  方式で組み、`tools/verify.mjs`の速度計測(次節)で「CPU合成のまま
  どこまで持つか」を数値化し、次回のEGC高速化との比較材料にする方針にした。
- シフト自体はソース1バイトにつき`>>`と`<<`を1回ずつ行うだけ(繰り上がり
  処理も1バイトにつき1回)で、事前シフト方式でも「どのシフト済みデータを
  選ぶか」の分岐は結局要ることを踏まえると、実装の複雑さの差ほど自明な
  有利さが無いと判断した。

**この判断は実測による直接比較(2方式を両方実装して比べる)ではなく、
上記の設計上のトレードオフによる判断であり、未確認のまま明記する。**
次回のEGC版との比較時に、必要ならこの判断も再検証する。

### クリップ・マスク合成の実装

1行(スプライトの1ソースバイト列)ごとに、出力先のバイト位置
(`startByte = (x - shift) / 8`から`shift?srcStride+1:srcStride`個)を
求め、各出力バイトについて「そのバイトに寄与する2つのソースバイト
(現在のバイトのシフトした上位側 + 1つ前のバイトのシフトした下位側)」
から合成する、という標準的な1bppブロック転送のシフト手法を使った。

- 画面外クリップ: 行(`scrY`)・出力バイト(`destByteIdx`)の両方を範囲外なら
  `continue`でスキップする(`p98_fill_rect`と同様、負の座標もそのまま
  比較できるようintで扱う)。
- マスク合成: 出力1バイトぶんのマスクとビットパターンをシフト計算した
  あと、`p98__blend_bits(seg,off,bits,mask)`(新規asmプリミティブ、
  `src/p98_asm.asm`)で`dst=(dst&~mask)|(bits&mask)`を1回のVRAM読み書きで
  行う。マスクが0(そのバイトは全ドット透明)なら4プレーンとも呼び出し
  自体をスキップする。

`p98__blend_bits`は既存の`p98__fillmem`と全く同じ引数パターン
(セグメント/オフセット/値/マスクをそれぞれ4バイトスロットの`[bp+N]`で
読み、VRAMセグメントをESへ直接ロードする)を踏襲しており、新規に
検証すべき呼び出し規約上の懸念は無い。

### 検証内容(`tests/probe_sprite.c`、詳細は`docs/verify-log.md`)

- 横1ドットシフト(shift=0〜7、バイト境界をまたぐ位置を含む)をVRAMの
  実バイト値(手計算した期待値)で確認。
- 複数色(4プレーンの組み合わせ)とマスクの穴の確認。
- 背景の矩形の上に穴あきスプライトを重ね描きし、穴からは元の背景の
  ビットが残ることを確認(マスクが本当に効いていることの検証。
  マスクを無視する故障注入版ではこの値が変わることも確認)。
- 画面の四隅・上下左右の端でのクリップ(はみ出し部分を書いていないこと、
  隣の行の先頭バイトを汚していないこと)。
- 故障注入: マスク無視版・横クリップ無し版がそれぞれ対応する検査で
  FAILする(検出できる)ことを確認。

### 速度の基準取り(`tests/probe_sprite_bench.c` / `probe_sprite_bench0.c`)

当初はゲスト側のBIOSティックカウント(INT1Ah、約18.2Hz)で、
`p98_wait_vsync()`36回ぶんの時間(vsync周期)とスプライト描画コストを
比較する計画だったが、実測すると**ゲストのBIOSティックがホスト
(puppeteer/headless Chrome)側の実時間と安定して対応しない**ことが分かった
(`docs/verify-log.md`参照。原因の特定はスコープ外)。そこでホスト側の
`performance.now()`で計測する方式に変更した: スプライトを2000本(16x16、
全ドット不透明、最悪ケース)描く版(`probe_sprite_bench.c`)と0本描く版
(`probe_sprite_bench0.c`、それ以外は同一)の実行時間を測り、差分を2000で
割って「スプライト1体ぶんの描画コスト」を求める。`tools/verify.mjs`実行時に
コンソールへ出力する(具体的な数値は`docs/verify-log.md`参照)。

**これは実機のfpsではなく、np2kai(WebNP2)+puppeteerというこの実行環境
全体を通した相対的な基準に過ぎない。** 次回EGCで高速化したときに同じ方式で
測り直し、比の変化を見るための基準線として残す。

## EGCによるスプライト高速化(2026-09後半。実装したが速くならなかった)

**【2026-09、訂正】** 本節はいったん「マスクもシフトも期待した使い方が
できなかった」と結論したが、その後**ユーザーの指摘を受けて前提を変えて
再実験したところ、シフトとマスクは正しい手順(読んでから書く)を踏めば
確実に機能することが判明した。** この訂正の詳細と実測の全条件表は
「EGCのシフト・マスク: 訂正(読んでから書く、が正しい手順だった)」節
(本ドキュメント後半)にまとめた。**以下の「結論を先に」以降(旧記述)は
歴史的経緯として残すが、「マスク・シフトは使えない」という結論部分は
古い誤りとして訂正済みである点に注意。** CPU代替として実装した
既存のEGC経路(`P98_SPRITE_EGC`、コミット`f5e14f6`)自体はこの訂正後も
変更していない(組み替えは次回以降のスコープ、後述)。

### 結論を先に(旧記述。訂正版は後述): EGCは速くならなかった(正直に報告する)

**今回試したEGCの使い方は、CPU合成(前節)より速くならなかった
(EGC/CPU比 約0.95倍。むしろわずかに遅い)。** 具体的な数値は
`docs/verify-log.md`参照。無理に速く見せる意図は無く、この結果をそのまま
報告する。理由の考察と次の手の候補は本節末尾。

**この評価は「4プレーン同時書き込みだけを使う」という限定的なEGC経路
(`P98_SPRITE_EGC`)についてのものであり、後述の訂正(シフト・マスクを
正しく使う経路)は速度未計測である。無理に速く見せないという方針は
訂正後も変わらない。**

### まず実測: WebNP2-wikiが「未検証」としていたマスク・シフトを測る

`WebNP2-wiki` `Graphics.md`のEGC節は、有効化手順(0x7Cのbit7→0x6Aを2回)、
プレーン選択(0x4A0)、パターン源(0x4A2)、WM(0x4A4)の基本、
ビット長(0x4AE)の既定値は実測済みだったが、**マスク(0x4A8)・
シフト(0x4AC)は「未検証」と明記されていた**。今回、使い捨てのプローブ
(コミットには残していない。他の節と同じ方針)で以下を実測した。

**マスク(0x4A8)**: WM(0x4A4)候補(0x0000/0x1000/0x2000/0x3000)×
マスク候補(0xFFFF/0x0000/0x0F0F/0xF0F0)×(事前の読み出し有り/無し)を
全組み合わせで試したが、**どの組み合わせでもビット単位の部分マスクには
ならなかった**。観測できたのは「全ビット上書き」「全く書けない
(元の値のまま)」「ゼロになる」のいずれかで、意図した
「マスク=1のビットだけ新しい値、0のビットは元の値を保持」という挙動は
一度も再現できなかった。wikiの「効果を確認できませんでした」という
記載と一致する結果になった。

**シフト(0x4AC)**: **バイト単位の書き込み(`mov [es:bx],al`や`stosb`)では
一切効果が無かった**。一方、**ワード単位の書き込み(`mov ax,[..]`で読み、
`mov [..],ax`で書く)では明確な効果があった**: レジスタ値をNとすると、
書き込んだワードの**偶数側(下位)アドレスのバイト**が `元の値 << (N-1)`
(8bit切り捨て、N=0とN=1はどちらも「シフト無し」)になった。ただし
以下の制限も同時に判明した:
- **書き込んだワードの奇数側(上位)アドレスのバイトは、どの実験でも
  一切更新されなかった**(元の値のまま)。単一の`mov`でも、
  `rep movsw`でも同じだった。
- **ワードをまたいだキャリー(繰り上がり)は発生しない**。1ワード内で
  シフトによりあふれたビットは捨てられるだけで、隣のワードには渡らない。
- VRAM上の可視領域外(セグメント内オフセット32000以降)は実際に
  読み書きできる領域だと確認できた(スクラッチ領域として使える)。
  そこにあらかじめ書いたデータを`rep movsw`でシフトしながら読もうとしたが、
  **EGC有効中の読み出しが実際の格納値を返さず、常に0になった**
  (WM=0x0000の場合。他のWMは未確認)。これにより「VRAM常駐のスプライト
  データをシフト転送する」という、実機PC-98ゲームでよく使われる本命の
  技法は、少なくとも今回試した設定では再現できなかった。

これらの実測結果はいずれも本ドキュメントとして初めて言語化したもので、
`WebNP2-wiki` `Graphics.md`へ書き戻せる内容(マスク・シフトの「未検証」の
解消、ただし「期待した使い方はできなかった」という形の解消)として残す。

### なぜ「マスク+シフトの組み合わせ」を諦めたか(旧記述。**訂正済み**、後述参照)

**この節の結論は誤りだったと判明した(後述の訂正節参照)。** 原因は
「シフト量」だと思っていた0x4ACレジスタが実際には「転送元ビット位置
(下位4bit)+転送先ビット位置(次の4bit)」という別の構造を持っており、
かつ0x4A4(WM/ope)に「シフトモード」を示す専用ビット(0x0800)を
立てていなかったこと、さらに何より**「読んでから書く」という手順を
踏んでいなかったこと**にある。以下は当時(誤った理解のまま)書いた
考察で、歴史的経緯として残す。

上記の実測から、当初期待していた「EGCで、4プレーン別々のスプライト
ビットマップを、シフト(1ドット単位の横移動)とマスク(透明ドット)を
かけながら1回の書き込みで転送する」という使い方は、この
np2kai実装では成立しないと判断した:
- マスクがビット単位で効かない以上、透明ドットを含むバイトをEGCだけで
  正しく合成する方法が無い。
- シフトはワード書き込みの片側バイトしか動かせず、キャリーも無いため、
  「ソース2バイトから出力1バイトを合成する」という今のCPU側アルゴリズム
  (`docs/design.md`前節)の代わりにはならない。
- VRAM常駐データからのシフト転送(読み出しを伴う本命の技法)は、
  読み出し自体が値を返さないため試せなかった。

### 採用した設計: 「全ビット不透明・4プレーン同一」バイトだけEGCで書く

上記を踏まえ、**確実に効くとwikiにも本実測にも裏付けがある機能
(WM=0x0000・プレーン全選択で、1回のCPU書き込みが4プレーンすべてに
同じ値を書く)だけ**を使うことにした。ソフトウェア側のシフト計算
(前節のCPU経路と全く同じ計算)はそのまま行い、出力1バイトぶんの
「マスク」と「4プレーンぶんの合成結果」が求まった時点で、

- マスクが`0xFF`(そのバイトは全ドット不透明)、かつ
- 4プレーンの合成結果が全プレーンで同一の値(単色スプライトの内部等)

の**両方を満たすバイトだけ**、4回の`p98__blend_bits`呼び出し
(1プレーンずつのread-modify-write)を、EGCを使った1回の書き込み
(`p98__pokeb`をB プレーンのアドレスへ)に置き換える。それ以外
(透明ドットを含む・プレーンごとに異なる色)は、確実性を優先して
従来のCPU経路のまま変えていない。

この設計により、**見た目の結果はCPU経路と常に一致する**
(透明ドットのある行・プレーンごとに異なる色の行はCPU経路そのまま、
単色・不透明の行だけ書き方が変わるだけで結果は同じになる設計)。
実際に`tools/verify.mjs`の等価性検査(次項)で、既存の`probe_sprite.c`と
全く同じ座標・スプライトデータをEGC経由で描いた`probe_sprite_egc.c`が、
**全く同じVRAMバイト列になる**ことを確認した。

EGCの有効化/無効化はバイトごとではなく、連続してEGC経路の対象になる
バイトの間は有効なままにし(`p98_draw_sprite`内の`egcActive`フラグ)、
CPU経路のバイトを挟むときだけ一旦無効化して個別プレーンの書き込みを行う
(有効なままだと、他プレーンへの書き込みへの影響が未検証のため。安全側に
倒した)。関数を抜けるときは必ず無効化し(`p98_quit()`側でも念のため
`0x7C=0`を叩く保険を追加した)、テキスト表示や次のDOSコマンド実行に
影響しないことを確認済み(`docs/verify-log.md`)。

### API: バックエンド切り替え

```c
typedef enum { P98_SPRITE_CPU = 0, P98_SPRITE_EGC = 1 } p98_sprite_backend_t;
void p98_set_sprite_backend(p98_sprite_backend_t backend); /* 既定: CPU */
p98_sprite_backend_t p98_get_sprite_backend(void);
void p98_draw_sprite_ex(const p98_sprite_t *spr, int x, int y, p98_sprite_backend_t backend);
```

`p98_draw_sprite()`は`p98_set_sprite_backend()`で設定した現在のバックエンドを
使う。検証(`tools/verify.mjs`)からは`p98_draw_sprite_ex()`で両方を
明示的に叩き分けられる。

### 等価性の検査(`tests/probe_sprite_egc.c`)

`tests/probe_sprite.c`(CPU経路)と全く同じ座標・スプライトデータを使い、
`p98_draw_sprite_ex(..., P98_SPRITE_EGC)`で描くだけの`probe_sprite_egc.c`を
作った。`tools/verify.mjs`は**同じ検査関数**を両方のプログラムの出力に
適用し、
- シフト0〜7(バイト境界をまたぐ位置を含む)
- 複数色・マスクの穴
- 重ね描き(マスクの穴から背景が見える)
- 画面四隅・上下左右の端のクリップ

の全シナリオで、CPU経路とEGC経路のVRAMバイト列が一致することを確認した
(結果は`docs/verify-log.md`)。

**故障注入**: 当初は0x4A0(プレーン選択)の設定を落とす/誤った値にする案を
試したが、**np2kaiのこのEGC実装では0x4A0の値に関わらず常に4プレーンぶん
書かれてしまい、故障として検出できなかった**(これも実測して初めて
分かったこと)。そのため、WM(0x4A4)を誤った値(0x1000=パターンを書く
モード)にする故障注入に変更し、これは等価性検査(の一部)が正しくFAILする
ことを確認した(`tests/p98_broken_egc_noplane.c`。ファイル名は当初の
0x4A0案の名残)。

### 速度のA/B比較: 結果は「速くならなかった」

`tests/probe_sprite_bench.c`(CPU、既存)と同一条件の
`tests/probe_sprite_bench_egc.c`(`p98_set_sprite_backend(P98_SPRITE_EGC)`
以外は完全に同一のコード)を用意し、共通のベースライン
(`probe_sprite_bench0.c`)との差分方式(前節と同じ、ホスト側
`performance.now()`)で比較した。条件は完全に同一: スプライト16x16
(全プレーン0xFF・マスク0xFFの最悪ケース、**このスプライトは全バイトが
EGC経路の対象になる**)、本数2000、同じ座標列、同じ測定方法。

**結果(2026-09、実行環境依存。詳細は`docs/verify-log.md`)**:
CPU経路 約268体/秒、EGC経路 約255体/秒、**比(EGC/CPU)= 約0.95倍
(EGCの方がわずかに遅い)**。

**これはnp2kai(WebNP2)のEGCエミュレーション実装+puppeteerという
この実行環境全体を通した相対値であり、実機での比率とは限らない
(エミュレータがEGCを実機より速く/遅く実装している可能性があるため)。**
定性的な結論として「このエミュレータ上では、今回の使い方のEGCはCPU合成
より速くならない」ことだけを採る。

### 考察: なぜ速くならなかったか(未確認の推測)

- 今回のEGC経路が削減できるのは「4回のread-modify-write呼び出し
  (`p98__blend_bits`)」を「1回の書き込み(`p98__pokeb`)」にする部分だけで、
  シフト計算自体はソフトウェアのまま変えていない。削減できる命令数に対し、
  EGCの有効化(`0x7C`/`0x6A`×2/`0x4A0`/`0x4A2`/`0x4A4`/`0x4A8`/`0x4AC`/`0x4AE`
  への計8回のOUT)のコストが、このエミュレータ上では相対的に重い可能性が
  ある(ポートI/Oのエミュレーションコストは未計測)。
- `egcActive`による有効化の使い回し(連続する対象バイトの間は無効化
  しない)はしているが、ベンチのスプライトは1体ごとに`p98_draw_sprite`を
  呼び直すため、**スプライト1体につき最低1回**は有効化/無効化のコストが
  乗る。スプライト1体あたりの出力バイト数(このベンチでは16x16で
  約16×3バイト=48バイト程度)に対し、有効化コスト(8回のOUT)の比率が
  無視できないほど大きい可能性がある。
- これらは**未確認の推測**であり、実際にボトルネックを特定する計測
  (例: 有効化コストだけを単体で測る)は今回行っていない。

### 次の手の候補(今回は実施していない)

- **EGCの有効化をスプライト1体単位ではなく、複数体の連続描画をまたいで
  使い回す**(呼び出し側が「これから複数体描く」区間を明示し、
  有効化/無効化を1回に減らす)。ただし他プレーンへの直接書き込みとの
  混在が安全か未検証(本ドキュメント前述の理由でバイト単位で切り替えている)。
- **GRCGのRMW(read-modify-write)モード**: `WebNP2-wiki`
  `Graphics.md`で「`0x7C`のbit7以外のビットは単純な書き込みでは差が
  出なかった」「読み出しを伴う動作モードがあると思われるが未確認」と
  されている部分を実測し、GRCG側にマスク付き合成の余地が無いか確認する。
- **転送単位の見直し**: 現在は1バイトずつ`p98__blend_bits`を呼んでいる。
  複数バイトをまとめて処理する(ループ自体をasm化する等)方が、
  EGCの有無に関わらずオーバーヘッド削減に効く可能性がある。
- **EGCのポートI/Oコスト自体の実測**: 「OUTを8回叩くコスト」だけを
  単体で測り、本当にそれがボトルネックかを確認する(今回は推測のまま)。

## EGCのシフト・マスク: 訂正(読んでから書く、が正しい手順だった)

### 発端: ユーザーからの指摘

前節の「マスクもシフトも期待した使い方ができない」という結論に対し、
「EGCのシフタ・マスクは“読んでから書く”対で初めて意味を持つ機構であり、
シフト無効化に見えた挙動は単に読み出し値そのものに意味が無いだけでは
ないか」「マスク・シフトのポート割り当て自体を疑うべき」という指摘を
受けた。指摘のとおり、前節の実験は**一度も正しい「読んでから書く」手順を
踏んでおらず**、また`NP2kai`側のソースを読んだ結果、レジスタの構造も
誤解していたことが分かった。

### 手がかり1: ユーザー本人の1997年のソース(参照可、ユーザー自身の著作物)

`_local/legacy-a-games/A-GAMES/KAKUTOU/KAKUTO.ASM`の`egc:`ラベル
(実装は空のまま止まっている、`docs/design.md`冒頭で既知)の**直前に
コメントアウトされた、より詳しい初期化コードが残っていた**
(未完成・未検証のコードで、そのままでは動かないバグもあると思われるが、
レジスタの値そのものは何らかの資料に基づいていたと考えられる、参考に
なる手がかり):

```asm
mov al,7   /  out 6ah,al        ; 拡張モード変更許可
mov al,5   /  out 6ah,al        ; EGC拡張モード
mov al,10000000b / out 7ch,al   ; GRCGモードレジスタ bit7
mov ax,0fff0h / out 04a0h,ax    ; access = 0xFFF0 (wikiの0xFF00とは違う値)
mov ax,00ffh / out 04a2h,ax     ; fgbg  = 0x00FF (wikiの0x02FF等とも違う)
mov ax,3100h / out 04a4h,ax     ; ope   = 0x3100
mov ax,0ffffh / out 04a8h,ax    ; mask  = 0xFFFF
mov ax,0      / out 04aah,ax    ; ★0x4AA という、wikiが一度も触れていない
                                 ;   レジスタに書き込んでいる
mov al,[シフト量テーブル] / out 04ach,ax  ; sft(シフト)
mov al,(横のドット数×16-1) / out 04aeh,ax ; leng(長さ)
...
rep movsw    ; DS=ES=BMEN(0xA800、同一セグメント内)でVRAM→VRAM転送
```

このコードは実行された形跡が無く、値をそのまま信用してよいものではない
(当てずっぽうの可能性も残る)。しかし**「0x4AAという未使用のレジスタが
存在する」「シフト値はテーブル引き」「転送はVRAM→VRAMのrep movsw」**
という3点の手がかりから、次に読んだNP2kaiソースの理解の裏付けとして
使えた。

### 手がかり2: NP2kaiソース(`../NP2kai/io/egc.c`, `mem/memegc.c`)

**注記: エミュレータの実装は「仕様の出典」としては扱わない。以下は
「なぜ前節の実測がうまくいかなかったか」を切り分けるために読んだもので、
結論はすべて本節後半の実測(VRAMの実値)で裏付けている。**

読んで分かった、前節の理解と違っていた点:

1. **`egc.h`のレジスタ名から、0x4A0〜0x4AEの正式な役割が判明**:
   `access`(0x4A0)・`fgbg`(0x4A2)・`ope`(0x4A4)・`fg`(0x4A6)・
   `mask`(0x4A8)・`bg`(0x4AA)・`sft`(0x4AC)・`leng`(0x4AE)。
   **0x4AAは「背景色」レジスタ**であり、wikiには記載が無かった
   (KAKUTO.ASMが触れていたのはこれだった)。
2. **`access`(0x4A0)は「1=そのプレーンへの書き込みをスキップする」という
   負論理のビットが下位バイトのbit0-3にある**
   (`egc_writebyte`/`egc_writeword`の`if (!(egc.access & 1)) { ...VRAM_Bへ書く... }`)。
   前節で試した0xFF00と0x0000は、どちらも**下位バイトが0x00で同じ**
   (=どちらも「4プレーンとも書き込む」)ため、この2値を比較しても
   差が出ないのは当然だった(故障注入で0x4A0を検出に使えなかった
   理由もこれで説明がつく)。
3. **`ope`(0x4A4)のbit11(0x0800)が「シフトモード」を示す**。
   前節で試した0x0000/0x1000/0x2000/0x3000はどれもbit11=0で、
   シフトパイプラインを使わない(または使っても出力先に反映されない)
   モードだった。
4. **`sft`(0x4AC)は「シフト量」ではない**。下位4bitが「転送元の
   ビット位置(srcbit)」、次の4bitが「転送先のビット位置(dstbit)」、
   bit12が方向、という構造(`egcshift()`関数)。前節では単純に
   0〜7を渡しており、これは「srcbit=0〜7、dstbit=0」を意味していた
   (=「転送先を動かす」のではなく「転送元を動かす」設定だった)。
5. **マスク(`mask`, 0x4A8)は、実際に書き込まれる`mask2`という別の
   内部変数に対し`mask2 = mask & srcmask`という形で使われ、`srcmask`は
   シフトパイプライン(読み出し時に更新される)由来**
   (`egc_opeb`/`egc_opew`)。**読み出しを一度も行わずに書くと、
   `srcmask`が不定(既定は0xffffだが、直前の操作で0になっている
   ことがある)のままマスクが決まってしまう**。
6. **読み出し(`egc_readbyte`/`egc_readword`)は、`ope`のbit10(0x400)が
   0のとき、読んだVRAMの内容をシフトパイプラインへ流し込む
   (`shiftinput_byte`/`shiftinput_incw`)**。前節で「EGC有効中の
   読み出しが値を返さない」と報告したのは、**読み出しの戻り値
   そのもの(CPUのAXに入る値)に意味が無いだけ**であり(実際、
   ope次第で`egc_src`や比較結果を返す設計になっている)、
   **読み出しという行為自体はラッチを満たすために必要**だった。
   ここがユーザーの指摘どおりだった。

### 実測: 条件を変えて全て記録する(表)

上記の理解に基づき、使い捨てプローブ(コミットには残していない)で
「読んでから書く」正しい手順を実測した。共通のレジスタ設定:
`access=0x0000`(全プレーン書き込み)、`fgbg=0x0000`、
`ope=0x08F0`(bit11=シフトモード、下位8bit=0xF0=ラスタ演算
「転送元をそのまま」= NP2kaiソースの`opefn`テーブルで`ope_f0`
[`return(&egc_src)`]に対応する値。**0xFFではなく0xF0**である点に
注意。0xFFは`ope_ff`[常に1]になり、これも前節で試していなかった
組み合わせ)、`bg=0x0000`、`leng`は転送ビット数に応じて設定。
手順は「レジスタを設定→ソースアドレスをワード単位で読む(`mov ax,[si]`)
→デストアドレスへワード単位で書く(`mov [di],ax`。書く値そのものは
無視される)」。

**表1: シフト(dstbit)を0〜7まで振る(srcbit=0固定、leng=15=1ワード)。
ソース(4プレーン、あえて別々の値にして多色判定を兼ねる):
B=0x00FF, R=0xFF00, G=0x0F0F, I=0xF0F0(いずれも読み出しアドレスの
低byte,高byteの順で解釈した16bit値)。デストは毎回0でリセット。**

| dstbit(sft) | Bplane結果 | 期待値(元の16bit値を右にdstbitぶんシフト) | 一致 |
|---|---|---|---|
| 0 | ff 00 | 0xFF00>>0 = ff00 | ○ |
| 1 | 7f 80 | 0xFF00>>1 = 7f80 | ○ |
| 2 | 3f c0 | 0xFF00>>2 = 3fc0 | ○ |
| 3 | 1f e0 | 0xFF00>>3 = 1fe0 | ○ |
| 4 | 0f f0 | 0xFF00>>4 = 0ff0 | ○ |
| 5 | 07 f8 | 0xFF00>>5 = 07f8 | ○ |
| 6 | 03 fc | 0xFF00>>6 = 03fc | ○ |
| 7 | 01 fe | 0xFF00>>7 = 01fe | ○ |

R/G/Iプレーンも同様に、それぞれの元の値を同じだけ右シフトした結果と
**全dstbitで一致した**(例: dstbit=1でR=00 7f、G=07 87、I=78 78。
`docs/verify-log.md`に生ログを残す)。**バイト境界をまたぐキャリー
(繰り上がり)が、4プレーンとも独立して正しく発生している。**
前節で「奇数アドレスは更新されない」「キャリーが無い」としていたのは、
シフトモード(ope bit11)を立てておらず、かつ読み出しを経ていなかった
ための誤りだった。

**表2: マスクを振る(dstbit=0固定、leng=15)。ソース=0xFFFF全プレーン、
デストは事前に0xAAAA(10101010の繰り返し)にしておく。**

| mask(0x4A8) | 結果(偶,奇バイト) | 解釈 |
|---|---|---|
| 0xFFFF | ff ff | 全ビット上書き |
| 0x0F0F | af af | 各バイトの下位4bitだけ上書き(0xAA=10101010の下位4bit 1010→1111、上位4bitは元のまま1010→**1010 1111=0xAF**、手計算と一致) |
| 0xF0F0 | fa fa | 各バイトの上位4bitだけ上書き(**1111 1010=0xFA**、一致) |
| 0x00FF | ff aa | **偶数アドレスのバイトだけ**上書き(マスクレジスタの下位byteが偶数アドレス側に対応) |
| 0xFF00 | aa ff | **奇数アドレスのバイトだけ**上書き(マスクレジスタの上位byteが奇数アドレス側) |
| 0x0000 | aa aa | 無変化(全ビット保持) |

**マスクはビット単位で正確に機能した。** 前節の「効果が無い/全消去/
全上書きのいずれかにしかならない」という結果は、シフトモードに
入っていなかった(=`srcmask`が不定または無関係な値のままだった)ことが
原因だったと判断できる。

**表3: シフトとマスクの同時適用(dstbit=3, mask=0x0F0F, ソース=0xFFFF,
デスト初期値=0xAAAA)。** 結果: `af af`。手計算: ソースを3ビット右
シフトすると各バイト`1f`,`ff`。マスク`0x0F0F`(各バイト下位4bitのみ
上書き)を適用すると、`1f`の下位4bit`1111`と元`aa`の上位4bit`1010`を
合わせて`1010 1111=af`、`ff`の下位4bitも`1111`で同様に`af`。
**実測`af af`と完全に一致。シフトとマスクは正しく併用できる。**

**表4: 2ワード(4バイト)の連続転送(実際のスプライト1行を想定)。**
`dstbit=3`固定、`leng=31`(2ワード=32bit)。ソース(4バイト、B平面のみ
確認)= `FF FF 00 00`。手順: 1語目を読んでdst位置0へ書く→2語目を
読んでdst位置2へ書く、を連続して行う。結果: `1f ff e0 00`。手計算:
32bit値`FFFF0000`を右へ3ビットシフトすると`1FFFE000`
(バイト列`1f ff e0 00`)。**実測と完全一致。ワードをまたいだ
複数回のread/writeでも、シフトの繰り上がりが正しく連鎖する**
(=スプライトの1行(複数バイト)をこの手順でまとめて転送できる見込みが
立った)。

### この訂正で分かったこと・まだ分かっていないこと

**分かったこと**:
- EGCのシフト・マスクは、`ope`にシフトモードビット(0x0800)を立て、
  「ソースをワード単位で読んでから、デストをワード単位で書く」手順を
  踏めば、複数プレーン・複数ワードにわたって正しく機能する。
- ただし**シフト元は必ずVRAM上のデータでなければならない**(EGCの
  読み出しはVRAMアドレスに対する操作であり、CPU/メインメモリ上の
  配列を直接シフト元にはできない)。これは前節でも判明していたことで、
  今回の訂正後も変わらない制約。

**まだ分かっていないこと(未確認)**:
- バイト単位(`egc_readbyte`/`egc_writebyte`、`mov al,[..]`/`mov [..],al`)
  でも同様にシフト・マスクが機能するかは、今回はワード単位でしか
  確認していない。
- `p98_draw_sprite()`の実データ(CPU側の配列)をEGCで扱うには、
  描画のたびにスプライトの各行をVRAM上の空き領域(オフセット32000
  以降。書き込み・読み出しできることは確認済み)へ**転送(ステージング)
  してから**EGCで読み出す、という一段階が必要になる。この
  ステージング自体のコスト(CPU側での書き込み)が、EGCで浮く分
  (シフト計算とマスク計算をハードウェアに任せられる分)を上回るかは
  **未計測**。
- 上記を踏まえた`p98_draw_sprite()`の全面組み替え(EGC用のステージング
  バッファを持つ設計への変更)は、**今回は実施していない**。
  レジスタ設定・手順の実証(本節)までに留めた。次回、
  ステージングを含めた実装とA/B速度比較を行う。
- 既存のEGC経路(`P98_SPRITE_EGC`、`p98_draw_sprite_ex`)は本訂正後も
  変更していない。CPU経路との等価性・速度比較(前節)はこの
  「4プレーン同時書き込みのみ使う」旧経路についての結果のままである。

## 動くデモ(`samples/walk.c`)と使い勝手で気づいた点(2026-09)

「全部が繋がって動く」ことの証明として、方向キーで8x8のキャラクタを動かし、
SPACEで色を変え、ESCで終了するデモ(`samples/walk.c`)を書いた。背景は
横1本のバンドと装飾矩形2つ(`p98_fill_rect`)。検証は`tools/verify.mjs`
(後述)。実装しながら気づいた、ライブラリの使い勝手についての所見を
そのまま書く(**API変更の判断は今回はしない**。明らかに小さく足せるものだけ
足し、足したものはここに列挙する)。

### 背景の退避・復元は完全に利用者任せ(最も大きな引っかかり)

`p98_flip()`はページを入れ替えるだけで、「前のフレームで描いた内容を
新しい描画ページにも反映する」機能は無い。つまり、キャラクタのような
動くものを描くたびに、**利用者が「元いた場所を背景で上書きする」処理を
自分で書く必要がある**。今回のデモでは最も単純な対策(毎フレーム背景
全部を描き直してからキャラクタを描く)を採ったが、これは背景が
矩形塗りだけの軽いものだから成立する方法で、背景が複雑・重い場合
(画像を敷き詰める、地形を差分更新したい等)には別の対策
(dirty rect管理、オフスクリーン合成用の元絵バッファ)が要るはずで、
p98libはそちらを支援するAPIを持たない。この点は`tests/walk_broken_nobg.c`
(背景復帰の呼び出しを1つ削除するだけでキャラクタの残像が永久に残る
デモ)で実際に確認できる。「p98libは背景管理をノータッチにする」という
設計判断自体はミニマルライブラリとして妥当だが、サンプル(`samples/hello.c`)
や`p98.h`のコメントには、この設計上の制約(「動かす前提のシーンでは毎回
背景を描き直すか、自分でdirty rect管理をする」)を明記していなかった。
**今回小さく足したもの**: `p98.h`の`p98_flip()`のコメントへ一文追記
(後述)。

### スプライトの色を変える手段が無い(struct固定なので複数用意することになる)

`p98_sprite_t`は4プレーン+マスクへの生ポインタを持つ構造体で、
「同じ形で色だけ変える」ことをサポートするAPIが無い。今回のデモでは
色ごとに`static const p98_sprite_t`を4つ用意し、ポインタ配列で
切り替える方式にした(`CHAR_SPRITES[colorIdx]`)。検討はしたが避けた
選択肢: **実行時に`p98_sprite_t`のフィールド(`planes[0..3]`)を
書き換える方式**。この方式自体は動くはずだが、今回のスコープの
他のどのコード(`tests/*.c`)も一度も使ったことが無い「structの
フィールドへの実行時代入」という、huge model上での実測がまだ無い
パターンになる。デモの目的が「繋がって動くことの証明」である以上、
未検証のパターンを新規に持ち込むリスクは避け、静的な複数struct+
ポインタ切り替え(既存パターンの組み合わせ)に倒した。**結果として、
色数だけstructが必要になり、色数が増えるほど定義が煩雑になる**
(4色で4個の`static const p98_sprite_t`)。パレット差し替え型の
ゲームでは、色ごとにstructを複製するのは現実的ではなくなりそうで、
「マスク+単色ビットマップ+パレット番号」のような、もっと軽いAPIが
将来欲しくなる可能性がある。**今回はAPIを変えていない**(足すとしたら
次回、実際に複数色スプライトが必要なゲームを書いてから判断する)。

### スプライト用のビットマップデータを手で書くのが大変

`p98_sprite_t`の1プレーンは「1行=ceil(w/8)バイト、MSBが左端」の
生バイト列を手で16進で書く必要がある。今回は8x8の小さい絵だから
手計算(方眼紙的に1と0を並べてまとめる)で済んだが、16x16以上や
複数コマのアニメーションになると非現実的になりそうで、ドット絵
エディタ等からこの形式へ変換するツール(あるいは既存形式からの
コンバータ)が無いと実用のゲームを書くのは厳しい。**今回はスコープ外**
(ツール整備は次回以降の課題として書き残す)。

### 継続的に再描画し続けるデモの検証は、静止プローブと勝手が違う

これはライブラリではなく検証手法(`tools/verify.mjs`)側の気づきだが、
今後同種のデモを検証する時のために記録する。既存の`tests/probe_*.c`は
「1回描いたら`for(;;){}`で静止する」方式で、外部からのVRAM読み取りは
何回読んでも同じ値になることが保証されていた。`samples/walk.c`のような
「毎vsync描き続けるゲームループ」ではこの前提が崩れる:

- 切り分けの過程(使い捨てプローブ)で、`readMemory()`が読むのは
  「表示中のページ」ではなく「現在の描画/アクセスページ(ポート0xA6側)」
  らしいと分かった。`p98_flip()`は表示・描画の両ポートを同時に
  入れ替えるため、flip直後に外部から読めるのは「1つ前のイテレーションで
  描いた側」になる。起動直後でまだ1回しかflipしていない(=もう片方の
  ページが一度も描かれていない)タイミングで読むと、まっさらな未描画
  ページを読んでしまい、実際には正しく描けているのに「何も描けていない
  (全プレーン0)」ように見える。2回以上flipが済めばどちらのページも
  正しい内容を持つため、この問題は起きない(ループ回数1/2/3回の
  使い捨てプローブで実測して確認した)。
- 直前に重い処理(このプロジェクトの`probe_sprite_bench`のような
  2000本スプライト描画のA/B速度比較など)を行った直後は、ホストが
  混んでいるためかエミュレーションの体感速度が実時間に対して大きく
  遅れることがあり、数秒待っても上記の「2回目のflip」に届かないことが
  ときどきあった(タイミング依存で、常に起きるわけではない)。
- 対策として`tools/verify.mjs`に`readManyStable()`(複数アドレスを
  1回の`evaluate()`でまとめて読み、2回連続で同じ値になり、かつ
  全部0ではないことを確認するまで再試行するヘルパ)を追加した。
- それでも、装飾矩形1箇所の直接検査だけは、この対策後も稀に
  読み取りが安定して0のまま返ることがあった。同じ座標・同じ
  `p98_fill_rect`呼び出しを「1回描画して静止」「2000回ループしてから
  静止」という決定的な方式で検証すると常に正しい値が読めたため、
  **ライブラリ側のバグの証拠は無い**と判断し、この1箇所の検査は
  `tools/verify.mjs`の自動検査から外した(未確認のまま`docs/verify-log.md`
  に記録する)。デモ本体の背景・矩形描画は他の検査(バンド・キャラクタ・
  背景復帰)で確認済み。

### 今回、明らかに小さく足したもの(1件)

- `include/p98.h`の`p98_flip()`のコメントに、「p98_flip()自体は前フレームの
  内容を引き継がない。動くものを描くシーンでは、呼び出し側が毎フレーム
  背景を描き直すか、自分でdirty rect管理をする必要がある」という趣旨の
  一文を追記した(API・シグネチャの変更は無し。ドキュメントコメントの
  追記のみ)。
